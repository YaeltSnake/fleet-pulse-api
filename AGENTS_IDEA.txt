# Idea: Sistema Multi-Agente Especializado para Desarrollo de Software
# Contexto: Conversación 2026-06-24 — fleet-pulse-api / Claude Code

================================================================================
## CONTEXTO DE LA IDEA
================================================================================

Durante el desarrollo de una aplicación Java Spring Boot con arquitectura hexagonal
(Ports & Adapters) he estado usando Claude Code con "skills" especializadas:
archivos .md en .claude/skills/ que definen reglas de seguridad, arquitectura, JPA,
JWT, testing y diseño de API. Claude las carga como contexto adicional antes de generar código.

Descubrí que Claude Code puede spawnear subagentes especializados con el Agent tool.
Quiero evolucionar el modelo actual (un solo Claude con skills) hacia un sistema de
agentes con responsabilidades separadas que trabajen en conjunto, similar a un equipo
de desarrollo real donde cada persona tiene su especialidad.

================================================================================
## PROPUESTA: 5 AGENTES ESPECIALIZADOS
================================================================================

AGENTE 1 — INVESTIGACIÓN
  Función   : Buscar información en fuentes actualizadas y confiables antes de decidir
  Skills    : Evaluación de fuentes (docs oficiales, RFC, NIST, OWASP, blogs de ingeniería)
  Tools     : WebSearch, WebFetch, Read
  Cuándo usar: Antes de implementar cualquier feature nuevo, antes de adoptar una librería,
               cuando hay una pregunta técnica sin respuesta clara en el codebase
  Output    : Resumen de hallazgos con referencias y recomendación concreta

AGENTE 2 — CIBERSEGURIDAD
  Función   : Auditoría de seguridad del código, endpoints y configuración
  Skills    : OWASP ASVS 4.0.3, NIST SP 800-63B, JWT hardening, SQL injection,
               CORS, rate limiting, mass assignment, IDOR, supply chain
  Tools     : Grep, Read, Glob, WebSearch
  Stack     : Java Spring Boot REST API, Spring Security, JWT (JJWT), SOAP (JAX-WS)
  Cuándo usar: Antes de cada merge con cambios en auth/endpoints/acceso a datos,
               antes de un release, como gate obligatorio antes de pasar a producción
  Output    : Audit report con PASS/FAIL/CONDITIONAL y blocking items

AGENTE 3 — ARQUITECTURA
  Función   : Verificar que la arquitectura se mantiene limpia conforme el sistema crece
  Skills    : Hexagonal Architecture, Clean Architecture (Uncle Bob), CQRS, Event Sourcing,
               decisiones monolito vs microservicios, ArchUnit patterns
  Tools     : Grep, Read, Glob, WebSearch
  Cuándo usar: Cuando se agregan nuevas capas o módulos, cuando el sistema crece y hay
               dudas de si seguir en monolito o dividir en microservicios, cuando hay
               violaciones de arquitectura detectadas por ArchUnit
  Output    : Análisis de la arquitectura actual, recomendación de evolución, decisión
               documentada como ADR (Architecture Decision Record)

AGENTE 4 — CÓDIGO
  Función   : Implementación de features con reglas estrictas de calidad
  Skills    : Java 21 (Records, Sealed Classes, Virtual Threads), Spring Boot 3.5,
               JPA/Hibernate 6, testing (JUnit 5, Mockito, Testcontainers, AssertJ)
  Tools     : Read, Edit, Write, Bash, Glob, Grep
  Cuándo usar: Para implementar lo que los demás agentes ya planificaron y aprobaron.
               NUNCA implementa sin tener el plan del Agente de Planeación
               y la aprobación del Agente de Seguridad y Arquitectura.
  Output    : Código listo con tests, sin violaciones de arquitectura

AGENTE 5 — PLANEACIÓN
  Función   : Crear roadmaps detallados por fases y capas antes de implementar
  Skills    : Metodologías de desarrollo (iterativo por capas), estimación, gestión de
               deuda técnica, definición de exit conditions por fase
  Tools     : Read, Write, WebSearch
  Cuándo usar: Al inicio de cada fase para crear el plan de implementación capa a capa.
               El roadmap generado es el input del Agente de Código.
  Output    : Roadmap con fases, capas, prerequisites, exit conditions y orden correcto

================================================================================
## FLUJO DE TRABAJO ENTRE AGENTES
================================================================================

  [Nueva Feature]
       |
       v
  Agente 5 (Planeación) → Plan detallado por capas
       |
       v
  Agente 3 (Arquitectura) → Valida que el plan respeta la arquitectura
       |
       v
  Agente 2 (Seguridad) → Audita el diseño ANTES de escribir código
       |
       v
  Agente 4 (Código) → Implementa siguiendo el plan aprobado
       |
       v
  Agente 2 (Seguridad) → Segunda auditoría sobre el código generado
       |
       v
  [Código listo para merge]

  Agente 1 (Investigación) se usa transversalmente cuando cualquier otro agente
  necesita información externa (nueva librería, mejor práctica, CVE, etc.)

    Regla clave: fork hereda contexto → prompt corto. Los demás empiezan en cero → hay que explicarles todo en el prompt.

    Ejecución en paralelo: Si mandas múltiples Agent calls en el mismo mensaje, corren simultáneamente. Por ejemplo: uno investiga seguridad, otro investiga arquitectura → al mismo tiempo → resultados en ~30% del tiempo.

    Lo que hay que ajustar:

    Los agentes no se comunican directamente entre ellos. La orquestación siempre pasa por el Claude principal (yo). El flujo real es:

    Tú → Claude principal
            ↓ spawns
       Agente Investigación  ←→  resultado → Claude principal
       Agente Arquitectura   ←→  resultado → Claude principal
            ↓ sintetiza
       Agente Código         ←→  resultado → Claude principal
            ↓ reporta
    Tú ← Claude principal

    No existe un bus de mensajes entre agentes. Es siempre hub-and-spoke con el Claude principal en el centro.

    Agente que falta en tu lista:

    Agente de Tests — separado del de código. El agente de código genera la implementación, el de tests genera la suite independientemente. Los test suites escritos por alguien que no escribió el código encuentran más bugs.

    COMO CREAR AGENTES - CON SEPARACION DE RESPONSABILIDADES
    Cómo crear un custom agent en Claude Code

    Crea un archivo .md en .claude/agents/:

    ---
    name: security-auditor
    description: Run security audit on Java REST API code changes. Use before any merge touching auth, endpoints, or data access.
    model: sonnet
    tools: [Glob, Grep, Read, WebSearch, WebFetch]
    ---

    Eres un auditor de seguridad especializado en Java Spring Boot.
    Stack: Spring Security, JWT (JJWT), JPA, SOAP (JAX-WS).
    Standard: OWASP ASVS 4.0.3 Level 2 + NIST SP 800-63B.

    [contenido de la skill 01-security-audit aquí]

    El campo description es crítico — Claude Code lo lee para decidir cuándo auto-sugerir el agente. Escríbelo como "cuándo usarlo", no "qué hace".

    Tools disponibles: Glob, Grep, Read, Edit, Write, Bash, WebSearch, WebFetch, Agent (y más). Declaras solo los que el agente necesita — principio de mínimo privilegio.

    Model override: Puedes usar haiku para agentes rápidos de búsqueda, opus para los de arquitectura/seguridad, sonnet para código. Optimiza costo.

Info esencial de Anthropic para empezar

1. Claude Code docs — claude.ai/code → docs → "Custom agents" y "Hooks"
2. El modelo de contexto: Fresh agents = zero context, siempre briefea completo. Fork = comparte caché, barato para derivaciones del trabajo actual.
3. Facturación: Cada agente consume tokens independientemente. Agentes paralelos cuestan lo mismo que secuenciales pero tardan menos.
4. Tool restrictions: En agents de investigación, no incluir Edit ni Write — principio de mínimo privilegio.
5. Output size: Los agentes devuelven un solo mensaje al final. Para reportes largos, hazlos escribir a un archivo temporal y leerlo después.
